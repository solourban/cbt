# CBT 코드 리뷰 및 리팩토링 계획

## 결론

현재 CBT는 정적 HTML 기반으로 실제 배포와 기출 데이터 검증에는 성공했지만, 장기 운영·유료화·법령 연계까지 가기에는 구조가 너무 뭉쳐 있다.

핵심 문제는 `index.html` 하나에 다음 책임이 동시에 들어가 있다는 점이다.

- React 앱 선언
- 화면 라우팅
- 문제 풀이 상태 관리
- 채점 함수
- localStorage 저장
- 프리미엄 잠금 UI
- 검색·북마크·오답노트
- OX·플래시카드 생성
- 스타일 정의

이 상태에서 기능을 더 붙이면 오류 원인 추적이 어려워지고, 특히 채점 오류처럼 특정 입력값에서만 깨지는 문제를 안정적으로 잡기 어렵다.

---

## 현재 코드 구조 리뷰

### 1. 정적 배포 구조

현재 `package.json`의 기본 빌드는 Vite가 아니라 `scripts/build-static.mjs`를 실행한다.

```txt
npm run build → node scripts/build-static.mjs
```

이 구조는 기존 정적 앱을 깨지 않기 위한 안전장치로는 적절하다.

다만 실제 운영 전환 시에는 Vite/React 앱으로 점진 이전해야 한다.

### 2. `index.html`의 과밀화

`index.html` 안에서 React UMD, Babel standalone, `config.js`, `questions.js`를 불러오고, 같은 파일 안에 전체 앱 로직을 선언한다.

문제점:

- 브라우저 런타임에서 Babel 변환이 필요해 초기 실행 비용이 크다.
- 함수 단위 테스트가 어렵다.
- 채점 함수 수정이 화면 전체 리스크로 번진다.
- 기능별 파일 경계가 없어 코드 리뷰가 어렵다.

### 3. 채점 함수 이중화

`src/lib/scoring.js`에 테스트 가능한 채점 함수가 이미 분리되어 있다.

하지만 실제 배포 앱은 아직 `index.html` 내부의 `grS`, `grE`, `grC`, `grSubs`를 사용한다.

즉, 테스트는 새 모듈을 보고 있고, 실제 서비스는 레거시 함수를 보고 있다.

이게 가장 위험하다.

현재 BUG-001도 이 계층 차이 때문에 단순 테스트만으로는 잡히지 않는다.

### 4. 데이터 구조

`questions.js`는 전역 `QUESTIONS` 배열이다.

장점:

- 정적 배포에 단순하다.
- Vercel 정적 호스팅과 잘 맞는다.

문제점:

- 문제 ID 중복, 필드 누락, 법령 개정 메타데이터를 강제 검증하기 어렵다.
- 법령 기반 문제의 현행성 여부를 자동 판별하기 어렵다.
- 특정 연도·회차·법령명 기준 인덱싱이 어렵다.

### 5. 저장소 상태

`config.js`에는 현재 실제 API 키나 관리자 코드가 없고, 공개 정적 배포용 주석이 명확하다. 이 방향은 맞다.

다만 유료화 전환 시에는 프리미엄 코드를 프론트에서 해시 비교하는 방식이 아니라 서버 검증으로 바꿔야 한다.

## 리팩토링 우선순위

### Phase 1. 안전 정리

목표: 기능을 바꾸지 않고, 현재 구조의 위험을 줄인다.

1. 코드 리뷰 문서화
2. QA 문서와 GitHub Issue 연결 유지
3. 채점 함수 테스트 케이스 확대
4. `index.html` 레거시 채점 함수와 `src/lib/scoring.js` 결과 차이 기록
5. 법령 연계 설계 문서 추가

### Phase 2. 채점 엔진 일원화

목표: 실제 서비스와 테스트가 같은 채점 함수를 보게 만든다.

1. `src/lib/scoring.js`를 기준 채점 엔진으로 확정
2. 레거시 `grS`, `grE`, `grC`, `grSubs`와 결과 비교 테스트 작성
3. `index.html`에서 동일 로직을 사용하도록 빌드 시 주입하거나, Vite 앱으로 이전
4. BUG-001 포함 P1 채점 오류 일괄 수정

### Phase 3. 앱 분리

목표: 화면·상태·도메인 로직을 분리한다.

권장 구조:

```txt

```

### Phase 4. 법령 연계

목표: 도시계획기사 문제를 법령 현행성·조문 근거와 연결한다.

## 법령 연계 설계

참고 repo: `chrisryugj/korean-law-mcp`

해당 repo는 법제처 API 기반 MCP/CLI로, 법령·판례·행정규칙·자치법규 등을 검색하고, 인용 검증·시점 비교·행위시법 판단까지 지원한다.

CBT에 바로 붙일 때는 MCP 서버를 프론트에서 직접 호출하면 안 된다. 정적 프론트에 API 키나 법제처 OC 키가 노출될 수 있기 때문이다.

권장 구조는 다음과 같다.

```txt
CBT Frontend
  ↓
Vercel Function / Supabase Edge Function
  ↓
korean-law-mcp 또는 법제처 API wrapper
  ↓
법제처 Open API
```

### CBT에 필요한 최소 법령 기능

1. 법령명 검색
2. 조문 조회
3. 특정 날짜 기준 법령 조회
4. 문제별 법령 근거 링크
5. 법령 개정 여부 표시
6. 문제 해설 내 조문 인용 검증

### 문제 데이터에 추가할 메타데이터

```js
lawRefs: [
  {
    lawName: "국토의 계획 및 이용에 관한 법률",
    article: "제36조",
    basisDate: "2026-01-01",
    note: "용도지역 지정 근거"
  }
]
```

### 화면 표시 예시

```txt
법령 근거
- 국토의 계획 및 이용에 관한 법률 제36조
- 기준일: 2026-01-01
- 상태: 현행 확인 필요
```

### 법령 현행성 처리 원칙

- 문제 출제 당시 법령과 현재 법령을 구분한다.
- 시험 대비용 문제는 `출제 당시 정답`과 `현행 법령상 표현`을 함께 보여준다.
- 법령 개정으로 정답이 바뀐 경우 문제에 경고 배지를 붙인다.

```txt
⚠ 법령개정 주의
출제 당시: 입지규제최소구역
현행: 도시혁신구역·복합용도구역 등으로 개편
```

## 1차 리팩토링에서 하면 안 되는 것

지금 바로 하면 위험한 작업:

- `index.html`을 한 번에 Vite 앱으로 갈아엎기
- 법제처 API를 프론트에서 직접 호출하기
- 프리미엄 검증을 프론트 코드에 추가하기
- BUG-001만 단독 수정하고 QA를 멈추기
- 문제 데이터 전체를 한 번에 변환하기
