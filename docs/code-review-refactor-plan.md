# CBT 서비스 코드 리뷰 및 리팩토링 계획

## 목적

현재 CBT 서비스는 기존 정적 HTML 앱을 유지하면서 Vite/React 전환 준비 코드와 기출 업데이트 파이프라인이 함께 들어간 상태다.

이 문서는 현재 구조의 문제를 정리하고, 배포를 깨지 않는 선에서 단계적으로 리팩토링하기 위한 기준 문서다.

---

## 현재 구조 요약

### 1. 실제 배포 앱

현재 실제 배포 앱은 루트의 정적 파일을 기준으로 동작한다.

```txt
index.html
config.js
questions.js
```

`package.json`의 기본 빌드 명령도 Vite가 아니라 정적 빌드 스크립트를 실행한다.

```bash
npm run build
# node scripts/build-static.mjs
```

### 2. 기출 업데이트 반영 방식

`questions.js` 원본을 직접 수정하지 않고, `scripts/build-static.mjs`가 빌드 시점에 `src/data/updates/merge-selection.js`의 우선 후보 문제를 `dist/questions.js`에 append한다.

장점:

- 원본 `questions.js`를 덜 건드림
- 배포 안정성이 높음
- 후보 문제를 빠르게 화면에 반영 가능

단점:

- 실제 서비스 데이터와 소스 데이터가 분리되어 추적이 어려움
- 장기적으로는 `questions.js`를 모듈 데이터로 이전해야 함

### 3. Vite/React 전환 준비 상태

`src/App.jsx`와 `src/lib/scoring.js`는 존재하지만, 실제 배포 앱은 아직 루트 `index.html`이다.

`src/App.jsx`는 현재 실제 서비스 화면이 아니라 채점 엔진 분리 확인용 임시 화면이다.

### 4. 채점 엔진 상태

`src/lib/scoring.js`에는 테스트 가능한 채점 함수가 분리되어 있다.

하지만 실제 정적 앱의 `index.html`은 아직 내부 함수 `grS`, `grE`, `grC`, `grSubs`를 직접 사용한다.

즉, 채점 함수가 두 벌이다.

```txt
index.html 내부 채점 함수 = 실제 서비스 사용
src/lib/scoring.js = 테스트 가능한 분리 모듈, 아직 실제 서비스 미사용
```

## 주요 문제점

## 1. `index.html` 비대화

### SO WHAT?

앱 전체 로직, 상태, 화면, 채점, 저장, 유료 잠금, 모의고사, OX, 플래시카드가 한 파일에 몰려 있다.

### WHY SO?

현재 `index.html`은 React UMD와 Babel을 직접 불러오고, `<script type="text/babel">` 안에서 전체 앱을 실행한다. 이 구조는 빠른 MVP에는 맞지만, 유지보수·테스트·유료화·보안 점검에는 불리하다.

### 리스크

- 작은 수정도 전체 앱에 영향을 줄 수 있음
- 함수 단위 테스트가 어려움
- 채점 오류처럼 한 함수가 터져도 원인 추적이 어려움
- Vite 전환과 정적 앱 유지가 혼재됨

---

## 2. 채점 로직 중복

### SO WHAT?

실제 서비스와 테스트 코드가 서로 다른 채점 함수를 사용하고 있다.

### WHY SO?

`src/lib/scoring.js`는 테스트 가능한 구조지만, 실제 배포 앱인 `index.html`은 아직 이 모듈을 사용하지 않는다.

### 리스크

- `scoring.test.js`가 통과해도 실제 화면 오류가 남을 수 있음
- BUG-001 같은 텍스트 입력 시 채점 무반응 오류가 테스트에서 잡히지 않음
- 리팩토링 후 어느 채점 함수가 진짜인지 헷갈림

---

## 3. 데이터 파이프라인 이중화

### SO WHAT?

기존 문제 데이터와 신규 후보 데이터가 서로 다른 위치에 있다.

### WHY SO?

원본 `questions.js`는 유지하고, 신규 후보는 `src/data/updates/*`에서 관리한 뒤 빌드 때 `dist/questions.js`에 붙인다.

### 리스크

- 화면에 보이는 데이터와 원본 데이터가 다름
- 중복 ID, 보류 문제, 후보 문제 추적이 어려움
- 장기적으로 관리자 페이지나 DB 전환 시 마이그레이션이 복잡해짐

---

## 4. 유료 잠금 구조의 한계

### SO WHAT?

현재 유료 잠금은 프론트엔드 localStorage와 월별 코드 검증 중심이다.

### WHY SO?

MVP 단계에서는 간단하지만, 실제 판매형 서비스에서는 클라이언트 코드만으로 접근권한을 완전히 보호하기 어렵다.

### 리스크

- 코드 로직이 프론트에 노출됨
- 사용자가 localStorage를 조작할 수 있음
- 결제·환불·권한관리·기기 제한 등 운영 기능 확장이 어려움

---

## 5. QA와 코드 변경 프로세스는 좋아졌지만 자동화는 아직 약함

### SO WHAT?

QA 문서, 이슈 장부, Issue 템플릿은 준비됐지만, 실제 화면 기반 테스트 자동화는 없다.

### WHY SO?

현재 GitHub Actions는 빌드와 정적 데이터 검증 중심이다. 브라우저에서 버튼을 누르는 E2E 테스트는 아직 없다.

### 리스크

- 배포는 성공하지만 화면 버튼이 무반응일 수 있음
- BUG-001 같은 오류를 자동으로 잡기 어려움

---

## 리팩토링 원칙

1. 한 번에 Vite로 갈아엎지 않는다.
2. 현재 정적 앱 배포를 유지한다.
3. 먼저 문서화와 테스트 가능한 순수 함수 분리부터 한다.
4. 실제 화면에 영향이 있는 변경은 작은 PR로 나눈다.
5. BUG-001 같은 P1 오류는 전체 QA 후 묶어서 수정한다.
6. 원본 문제 데이터는 대형 변경 전에 백업과 검증 스크립트를 먼저 둔다.

## 현재 결론

현재 서비스는 MVP로는 잘 진화하고 있지만, 판매형 서비스로 가려면 다음 순서가 맞다.

```txt
정적 앱 유지
→ QA로 오류 수집
→ 채점 로직 표준화
→ 데이터 검증 강화
→ UI 모듈화
→ Vite 전환
→ Supabase/유료화
```

지금 당장 가장 위험한 부분은 `index.html`에 남아 있는 레거시 채점 함수와 실제 테스트 코드가 바라보는 `src/lib/scoring.js`가 분리되어 있다는 점이다.

따라서 다음 실제 리팩토링은 채점 로직부터 들어가는 것이 맞다.
